# 证明边界 / Proof Boundary

> 一个门禁工具最不能输的仗，是对「自己能证明什么」绝对诚实。此表是 SpecNotary 对外承诺的唯一口径；任何宣传语与此表冲突时，以此表为准。

## PASS 的准确含义

`RESULT: PASS` 表示：**在已声明的范围与确定性规则内，规格结构自洽、引用闭合、派生物与准据同源、原料登记基于未变化的内容快照。**

`RESULT: PASS` **不**表示：需求在业务上完整、真实、正确，或原型行为已被验证。

## 逐项边界

| 说法 | 门禁能证明 | 门禁不能证明 | 补位机制 |
|------|-----------|--------------|----------|
| 机读通过硬门禁 | Schema 合法；ID 唯一（含跨类型不撞车）、引用闭合、不自相矛盾（scope / 矩阵 / 职责）；ready 完备性（无空话、无占位、无未决） | 业务语义正确、方案合理 | 人的评审；假设/决策显式登记后供人拍板 |
| 人读没漂 | 人读正文与当前机读、当前渲染器逐字同源（spec_hash + body_hash + renderer_version）；来源声明 `generated_from` 确指被检查的机读文件 | 机读本身正确 | 上一行 |
| 原料没漏 | 原料文件内容快照（content_hash）未变；`evidence` 引文与 `source_ref` 指向的文件名一致（换文件即暴露）；已登记 claims 处置合法、引用真实；每个必选实体被 claim 引用 | 原料的每一句话都被登记（账本由起草方自报） | 原料一变即全体 claims stale；评审报告逐条列账供人抽查 |
| 方案没编 | assumption / conflict / pending / 未拍板 decision 均显式登记，且在 ready 上被硬拦 | 起草方没有把猜测直接写成 covered 事实 | 起草与审查分离（双 Agent / 人审）；SourceClaim 需带证据位置 |
| 原型没跑偏 | manifest 与机读同源（hash）；必选实体映射齐全；`data-spec-id` 在 DOM/JSX 真实落点；声明的交互链路 ID 闭合 | 文案、视觉、交互行为、业务结果与规格一致 | `semantic_warnings`（WARN 层）；人工走查；背书须显式（`sync --attest-prototype`） |
| PASS 即评审就绪 | 结构与证据链已闭合，评审可以聚焦语义 | 事实为真、利益相关方已确认 | 评审会本身 |

## 两类哈希的不同效力（重要）

- **人读哈希是派生证明**：人读确实由机读重新渲染，比对是逐字的。效力最强。
- **原型哈希是背书声明**：原型不会被本工具重新生成；`generated_from_spec.hash` 只表示「有人声明原型对应此版机读」。因此 `sync` 默认**不**刷新它——机读变更后原型哈希保持 stale FAIL，直到人/Agent 复核原型并显式执行 `sync --attest-prototype`。背书是动作，不是副作用。

## 规则覆盖度量（为什么这张表可以被信任）

「门禁有哪些规则」不靠记忆，靠度量：`tests/test_mutations.py` 是变异矩阵——按「变异算子 × 机读对象族」系统枚举坏输入（类型错误 / 重复 ID / 悬空引用 / 自相矛盾 / 占位空话 / 证据缺失），每个变异都必须被某条规则击杀，输出 `KILL_RATE` 并进 CI。新增对象若不补变异算子，矩阵自身的守卫测试会 FAIL。

两轮外部与内部审计共发现 20 个规则缺口，全部已转为矩阵中的变异用例——这条覆盖曲线本身就是此表可信度的来源。

## 自报闭环的结构性上限

同一个 Agent 可以完成「读原料 → 写机读 → 写 claims → 造原型 → 写 manifest → 跑门禁」。确定性门禁能验证这份账本的格式、引用与快照一致性，**不能仅凭账本本身证明账本没有隐瞒**。降低此风险的手段是流程性的：起草者与审查者分离、原料哈希钉死快照、假设必须显式、评审报告把账本摊开供人抽查。这是工具必须长期尊重的能力上限，也是我们不把「原料没漏」写成绝对承诺的原因。
